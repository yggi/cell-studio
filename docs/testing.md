# Testing

What the tests promise and how to run them; see [architecture.md](architecture.md) for the code they cover.

## Run

CI (`.github/workflows/ci.yml`, Node 22) is the gate on every PR and on `main` (the ruleset requires the `check` job; see [decision 004](decisions/004-agents-dont-merge.md#the-ruleset)):

- `static` job: `npm run check` (svelte-check with `--tsgo`: the TypeScript diagnostics come from the native compiler, `@typescript/native-preview`, pinned; the same diagnostics as `tsc` in about a third of the time; then `tools/strict.mjs`, a ratchet: `src/**/*.ts` checked with `noUncheckedIndexedAccess` (`tsconfig.strict.json`; not tests, not `.svelte`), failing on any error in a folder on its clean list, `audio/`, `midi/`, `theory/`, `ui/*.ts`, `ui/state/`, `ui/kit/`, and of the engine `fold/`, `midiimport.ts`, `time/structure.ts`, `readers.ts`, and of the layout `envelope.ts`, `glyph.ts`, `timelayers.ts`, `timepictures.ts` (#320: new code goes on clean); a folder made clean goes on the list), `npm run lint` (ESLint: `typescript-eslint` and `eslint-plugin-svelte`, `eslint.config.js`; errors fail, warnings are listed), `npm run format:check` (Prettier: `.prettierrc.json`, `.prettierignore`; `npm run format` fixes), `npm run knip` (unused exports, files and dependencies: `knip.json`), `npm run build`. It uploads the build.
- `test` jobs: the vitest suite in its two projects (`vite.config.ts`), one runner each, with `--bail 1`: `quick` (every test but the heavy sweeps) and `slow` (`*.slow.test.ts`: the folder over whole pieces and over the MIDI library, the ratchets), each whole, on every run: the gate doesn't pick what to run. `static` and the two run side by side, and the `check` job passes when all three have passed (it is the one status the ruleset requires).
- Smoke test (`.github/workflows/smoke.yml`, not part of `ci.yml`; its `repeatable` job, beside `smoke`, renders every example twice, below): `npm run smoke` on a fresh build, in the runner's Chrome: `tools/smoke.mjs` opens every piece of the library and presses Play (its voices are built and its first window is asked for), and plays in full, for 2 s, the fewest pieces that between them use every kind of audio node: each voice source and body, every sound parameter set or moving, tapes and their parts, kits, gates, bends, envelopes (`tools/smoke-pick.ts` works them out from what each example compiles to, so a new example that brings a new kind of sound is played by itself; `npm run smoke -- --list` says which and why). It fails on any page error, console error, or an AudioContext that isn't running (and, played in full, advancing). This is the only check that builds the audio graph of every voice kind (tapes, resonators, FM, kits), since vitest has no Web Audio. `--all` plays every piece in full. Then `tools/repeatable.mjs 4` renders every example offline twice, 4 s each: the two renders must be **the same sound** (below), none of our code may call `Math.random`, and no piece may clip or go over the loudness ceiling (peak −1 dB, average −18 dB; a ceiling only, since 4 s of a quiet start averages far under the piece's −24 dB). Together they take a few minutes and run on every PR that isn't a draft (on open, each push, reopen, ready for review); `main` doesn't run it. It isn't a required check: whoever merges waits for it on the head (the `senior` skill).
- The build is a PWA (`vite-plugin-pwa` in `vite.config.ts`): `dist/sw.js` precaches the shell and the Tone chunk; a new version waits for the user (`src/ui/UpdateToast.svelte`). `base` is `./`, so the same `dist/` works under `/cell-studio/` or any preview folder.
- `deploy` job (`main` only): publishes the `check` job's build to the root of gh-pages, keeping the `pr-<n>/` folders; it doesn't test or build again. A deploy running is never cancelled; a run whose commit is no longer the head of `main` skips, so the newest commit is the one that ends up live.
- `preview.yml` (on demand: put the `preview` label on a PR from a branch of this repository; not forks or Dependabot, whose token can't write): builds the PR on its own (no tests; `check` does those, so labelling re-runs nothing) and publishes it to `gh-pages/pr-<n>/`, at `https://yggi.github.io/cell-studio/pr-<n>/`, to try it on a phone before merging, rebuilt on every push while the label is on, with one comment on the PR with the address (found by a hidden marker and edited). Most PRs never need one, so none is made by default. `.github/workflows/preview-cleanup.yml` removes the folder when the PR closes with the label on, or the label is taken off, and says so in that comment; by hand (Actions → Preview cleanup → Run workflow, a PR number) for one left behind. By hand too: Actions → Preview → Run workflow, a PR number. The build is of the PR merged with `main`, as `check` tests it.
- Every gh-pages writer goes through `.github/scripts/pages.sh` (`main`, `preview <n>`, `remove <n>`): it makes gh-pages one fresh commit (no history of builds, as before) from the branch as it is, and pushes it with a lease on the commit it started from; if another writer got there first it starts again from theirs, so none overwrites another's folder. Concurrency groups only order the runs of one writer (`pages-main`; `pages-pr-<n>` for a PR's preview and its removal, a newer one cancelling the older): GitHub keeps one pending run per group and cancels the one before, so a single group for every writer could drop a removal or a preview.
- A preview shares the origin with the app: `src/storageKey.ts` gives its kept settings (`?latency=`, `?lookahead=`, `?perf`, the engine, the library's layout) keys of its own (`pr-12/cell-studio-latency`); the app keeps the plain keys. Saved pieces too (`library.ts`): a PR that changes how pieces are saved can't touch yours. The app's service worker doesn't answer for `pr-<n>/` pages (`navigateFallbackDenylist` in `vite.config.ts`), which would otherwise be served the app's own page.

Locally, run `npm test && npm run check && npm run lint && npm run format:check` before pushing, and one file while iterating (`npx vitest run src/engine/parser/parser.test.ts`, or `npx vitest run --changed`: the tests that import what you changed). Run the smoke test only when you changed what it covers (audio, UI wiring, assets, `vite.config.ts`): `npm run build && npm run smoke -- 2 "Music Box"` (seconds, then piece-title words, each played in full; all pieces if none). In a cloud session set `CHROME_PATH=/opt/pw-browsers/chromium`.

### What `npm test` runs

`npm test` (`tools/test.mjs`) runs every quick test, and a slow test only when the change reaches it: when the slow file, or anything it imports, differs from `origin/main` (committed, staged, changed or new: vitest's `--changed`), or a file the tests read from disk moved (`forceRerunTriggers` in `vite.config.ts`: `examples/`, `midi/`, the BWV 847 reference, the lockfile). It says which slow files it runs and why; the picked ones share one vitest run with the quick ones. Every slow test runs on CI (`CI` set), with no `origin/main` to compare with, or when vitest can't list what changed. `npm test -- --all` (or `npm run test:all`) runs everything; `npm run test:slow` the slow project alone; `npm test -- <file>` runs what you name, in whichever project.

- **Quick or slow.** A test belongs in the slow project (`name.slow.test.ts`) when it takes more than a few seconds idle: a sweep that folds whole pieces, or a ratchet over a library. Quick tests have 20 s each (`testTimeout`) and show their time past 5 s (`slowTestThreshold`): one that does, often, is a candidate for the slow project. Slow tests have 10 min each: a budget for a loaded machine, not a measure; they fail on what they find, not on the clock (#361).
- **Idle, on 4 cores:** `npm test` for a change that doesn't reach the slow tests (UI, layout, docs) about 1 min; one that does (the engine, the folder, an example, a MIDI file) about 2½ min, as `test:all`. Before the split every `npm test` took 3 min, a 103 s test (the whole MIDI library folded in one file) its critical path; the library's ratchet now runs one file per collection (`fold/midiRatchet.ts`), side by side.

### Fail-safes

- **A stale build.** `smoke`, `repeatable`, `golden` and `shots` test `dist/`, not the source: each stops if a file the build is made from (`src/`, `public/`, `examples/`, `index.html`, `vite.config.ts`, the lockfile; not tests) is newer than `dist/index.html`, and names it (`tools/fresh-build.mjs`). `STALE_BUILD=1` tests the build as it is; `shots` with `DIST=` skips it (another build, on purpose).
- **A stale type-check cache.** `npm run check` first removes what svelte-check transpiled for components that are gone (`tools/check-stale.mjs`): a deleted component's leftovers in `.svelte-check/` reported errors from code that no longer exists.
- **A deploy by hand** (while CI is off, #300): `node tools/deploy.mjs` refuses a tree with changes or a HEAD that isn't `origin/main`'s, runs every check CI runs (`test:all`, slow tests too), builds afresh and only then publishes with `.github/scripts/pages.sh`. `--dry-run` stops before publishing.
- **A MIDI collection without its ratchet.** `fold/midi.sets.test.ts` (quick) fails when a set in `midi/` has no `midi.<set>.slow.test.ts` or no baseline.
- **Timing in the browser.** The smoke test's take (#210, #360) stamps each key with the moment its step is heard (`cellStudio.heardAt`), as a real MIDI message carries its `timeStamp`, and aims at the pass the recorder placed (`cellStudio.take()`): a loaded machine sending a key late doesn't move it. Under five busy loops on 4 cores the old check failed 3 runs of 3, the new one passed 3 of 3.

Tests are `*.test.ts` beside their source, in node (no isolation between files, and transformed modules cached on disk: `vite.config.ts`). Vitest runs files in parallel, not the tests in a file: a sweep over the whole library goes in a file of its own (`physics.library.test.ts`) and does each piece’s work once for all its checks. Being in node, they can only cover `engine/`, `layout/`, `theory/`, the audio engines (not Web Audio), a few `ui/` helpers, the examples and the docs.

## Groups

- Theory: `src/theory/modes.test.ts`.
- Parser: `parser/parser.test.ts`. The syntax reference: `parser/reference.test.ts` parses every example in `docs/language/reference.md` (generated by `tools/reference.ts` from the parser's tables), checks it covers every generator, `map=` kind, unit, modifier, attribute and parameter, and that the committed page is current (record it: `UPDATE_REFERENCE=1 npx vitest run src/engine/parser/reference.test.ts`). Compile: `compiler/compile.test.ts`, `duration.test.ts`, `physics.test.ts`, `fiveto12.test.ts`.
- Realize (what sounds): `realize.test.ts` (notes, times, levels, per example), `tape.test.ts`, `resonator.test.ts`, `fm.test.ts`, `wave.test.ts`; `edit.test.ts` for line rewrites; `schedule.test.ts` (windows, the engine host).
- Routing (what the graph draws as sounding): `routing.test.ts`: the cases of #11, and for every example that routed and live states agree (live within routed, edges with routed ends, every routed edge drawn), every voice that plays is routed and live while its note sounds, and what moves a voice is routed.
- Audio: `src/audio/engine.test.ts` (local and worker engines; no Web Audio needed).
- Layout: `src/layout/*.test.ts` (belts, cellview, describe, dial, geometry, labels, physics, quality, show, spectrum); `physics.library.test.ts` lays out every example (three times, for the quality gate).
- Examples: `src/engine/examples.test.ts` — every `examples/*.cells` file is listed, compiles with zero diagnostics, and has a title, tags, and its card's `postgain=` (left out where it is 1) or no card (the built-in card).
- Snapshot: `src/engine/snapshot.test.ts` — every example's notes over its first 40 s, the values its cells hold at four moments and the live view at three, hashed into one line per piece in `src/engine/snapshot.txt`; a change to what a piece plays fails and names it. Its `notes` column hashes only voice, onset, length and pitch: an `events` hash that changes with `notes` unchanged is a respelling (the tables spell a note differently) or a change in level, pan, bend, parameter or envelope: look. Beside it, for every example: two plans play the same, and 0–30 s plus 30–60 s is 0–60 s. **An intended change** to an example's notes refreshes the file (`npx vitest run -u src/engine/snapshot.test.ts`), and the PR names the pieces and says why; an unintended one is a bug. Spellings that should play the same (Shorten's check, the equivalence tests) are compared over one length, `SAMENESS_SECONDS` in `src/engine/shorten/harness.ts` (a minute: pieces whose layers turn slower, a day or twenty minutes, are not run to the end). It doesn't see the DSP (renders: `tools/golden.mjs`, #92).
- Equivalences: `src/engine/equivalence.test.ts` — spellings the language promises are equal play the same notes: `map=edo` and `map=ed(2)` (decision 003; at 12, 19, 31, and every example with its default grid written out), `scale(tonic, phase)` and a key and a mode written out (decision 002; six pairs, and every example that uses it), and Shorten run to the end has nothing left to say the second time (every example but BWV 847, for time).
- Fuzz: `src/engine/fuzz.test.ts` — every example with one token or character deleted (a seeded sample of 20 each) compiles, plans and plays its first seconds without throwing. A program with errors plays nothing (`plan` returns no tracks): it may name cells it doesn't have.
- UI helpers: `src/ui/colour`, `highlight`, `suggest` tests.

## Promises

- Shorten (`src/engine/shorten/`) preserves every note: `shorten/shorten.test.ts` runs `shorten` on every preset; each suggestion is shorter and `sounds()` is identical (events from `plan` + `eventsBetween`). `shortenAll` is tested too.
- BWV 847: `tools/bwv847.reference.json` (written by `tools/bwv847.py`, which downloads the CCARH encoding itself and also writes `examples/bwv847.cells`) is checked note by note in `realize.test.ts`: onset, length and pitch per voice, as sounded through the tempo map.
- Counterpoint: the Ricercar's passes obey the species rules in `realize.test.ts` (`problems(...)` on what sounds, also per tonos). `tools/counterpoint.py` searched for the lines under the same species rules.
- Loudness: not in vitest (needs Web Audio). Measure in the browser with `window.cellStudio` (defined in `src/debugHook.ts`):
  - `await cellStudio.measure(seconds?)` renders offline, returns `{ rms, peak, clipped }` (dB below full scale; `clipped` counts samples at the ceiling).
  - `cellStudio.length()`: default render length in seconds.
  - `cellStudio.level(name)`: a voice's current peak level, or `null`.
  - `cellStudio.transport()`: `{ state, seconds }`, the transport's state and where the piece is heard (code seconds).
  - `await cellStudio.render(source, seconds?)`: renders any source (not only the open piece); adds `hash` (of the samples) and `blocks` (the level of every 2048 samples).
  - `cellStudio.engine()`: how the engine's windows went (which engine, how many, compute and round-trip ms, how many a worker answered too late).
- **The same sound** means two renders whose levels agree block by block (every 2048 samples) within −100 dB: far below hearing and below the 0.1 dB the loudness checks work in. Bit for bit is neither reachable nor needed (below).
- A piece sounds the same every time (#37), as far as our code goes: none of it draws on `Math.random`; noise, a resonator's bow and where a noise note starts come from our own seeded generator (`src/audio/voice/noise.ts`) and the cell's `seed` (as chance does). Tone.js is left alone, and two parts of it draw on `Math.random`: the reverb's impulse and a tape's hiss. Two guards: `src/audio/repeatable.test.ts` (CI) scans `engine/`, `layout/` and `audio/` for `Math.random` and names the line; `tools/repeatable.mjs` (browser, `npm run build && node tools/repeatable.mjs 6 [piece words]`; the smoke workflow runs it at 4 s) seeds `Math.random` before each render (so Tone's part repeats), renders every example twice, fails on a call from our code (and prints the caller) and on two renders that differ beyond −100 dB. Not bit for bit: Chromium sums three or more inputs of a node in a changing order (about −180 dB; measured with plain oscillators into one gain). Forks and kalimba are listed as known (#65): their resonators form a feedback loop (`couple=`, a board), and Chromium seems to process a loop starting from a node that changes from run to run, so a link runs a block late (up to about −45 dB; without the loop both repeat bit for bit). Accepted: it can't be heard live, and only a worklet holding the whole coupled bank would make it repeat (#17).
- The corpus yardstick (#10, language and example changes): `tools/corpus.mjs` measures every example (characters, lines, cells, diagnostics, what Shorten still finds) and fingerprints the notes it plays (voice, onset, length, frequency and gains over 0–120 s, from `plan` + `eventsBetween`). Record on the base (`node tools/corpus.mjs > /tmp/corpus.json`), then check the change (`node tools/corpus.mjs --check /tmp/corpus.json`): it lists each piece whose notes or code moved and exits 1 when a piece sounds different, except those named with `--expect "acid,pop"` (the ones meant to). No build, a few seconds; notes, not audio (an audio change is `tools/golden.mjs`).
- Golden renders (audio refactors): `tools/golden.mjs` renders every example offline in the browser and compares block levels with a recorded run: record on the base commit (`npm run build && node tools/golden.mjs 6 > /tmp/golden.json`), then check the change (`… --check /tmp/golden.json`). Within −80 dB counts as the same; forks and kalimba vary by up to about −45 dB from run to run on their own (their feedback loops, #65), so a differing piece is rendered twice more before it counts. Not in CI: a stored golden needs a way to say a change to a sound is intended (#92); the repeatability run above and the event snapshot (#142) are what CI checks.
- Engines (#15): `src/engine/schedule.test.ts` (windows match `eventsBetween` and survive a structured clone; the host mirrors hands), `src/audio/engine.test.ts` (the worker engine through a fake port: same windows, a late or failed worker falls back to the local plan). In the browser: `ENGINE=worker npm run smoke` plays every piece with the engine in a Web Worker.
- Graph states in the browser: `node tools/gallery.mjs play` plays pieces and saves a screenshot and each node's and edge's drawn state (`node tools/gallery.mjs play 3 "Sound on Tape"`; `DIST=` another build to compare).
- Keyboard focus (#135): `tools/tabwalk.mjs` Tabs through the start view, the sidebar (Files, MIDI, the layout forces), Shorten, the legend, add a cell, the cards, a library piece, a cell's sheet and (at phone width) the Graph and Code tabs, and lists each stop whose computed outline and box-shadow draw nothing (`CHROME_PATH=/opt/pw-browsers/chromium node tools/tabwalk.mjs [stops] [view words]`, no build, the first load is slow; exits 1 when a stop has no ring). It checks that a ring is drawn, not what it looks like; a view it can't open is reported, and counts as a failure.
- Every graph at once: `tools/graphs.mjs` draws every example's miniature, as the library draws it, on one contact sheet with its crossings, overlapping clusters and intruders from the layout's baseline (`CHROME_PATH=/opt/pw-browsers/chromium node tools/graphs.mjs`, no build, a few seconds; writes `shots/graphs/sheet.png`).
- The gallery (`tools/gallery.mjs <wheels|edges|golden|mockups>`): contact sheets of how the graph draws things, one picture per kind. `golden` renders one piece, `tools/gallery/golden/golden.cells`, with a value of every kind of wheel and edge the examples draw, in the real graph laid out by the app (`golden.test.ts` checks its coverage and its layout); `wheels` plays every piece in the built app and keeps every kind of wheel (graph, petals, a cell's sheet, the library) in its liveliest state (`npm run build && node tools/gallery.mjs wheels`; writes `shots/wheels/sheet.png`); `--fast`, and `edges` (every kind of edge in every state, on bare nodes) and `mockups` (design questions side by side), set everything up directly instead (`tools/gallery/harness.html`, from the working tree, no build, ~15 s). The `gallery` skill (`.claude/skills/gallery/SKILL.md`) says how to read them and compare before / after.
- Layout quality (#27): `src/layout/quality.ts` measures a layout: drawn crossings, the box, mean edge length, the worst overlap, overlapping tag clusters and cells inside a cluster they don't carry. `physics.library.test.ts` measures every example (and its crossings before the physics, `start`), each number the mean of three starts (seeds 0, 1, 2), and compares the library's totals with `src/layout/quality.baseline.json`: crossings (and their cost), clusters, intruders and read heads' aim may not grow, the area not by more than 5 %. A layout change that is worth its trade records the new numbers (`UPDATE_LAYOUT_BASELINE=1 npx vitest run src/layout/physics.library.test.ts`), so the PR's diff of the baseline shows what it did, piece by piece. One layout is one draw: neighbouring settings move the library's crossings by ±15, so compare a change over several starts (`seed`, a layout option: which small nudges new nodes get; 0 is the app's), as in [notes/27-layout.md](notes/27-layout.md).
- The folder's ratchet (#307): `src/engine/fold/ratchet.slow.test.ts` takes every example the way a MIDI file comes in (saved as MIDI, opened again), folds it (`engine/fold`) and scores it against the example as written (`fold/score.ts`): its notes kept, its score's size, its phrases back. The totals are compared with `src/engine/fold/ratchet.baseline.json`: no piece that kept its notes may lose them, the phrases back may not fall, the score not grow by more than 1 %. A change worth its trade records the new numbers (`UPDATE_RATCHET=1 npx vitest run src/engine/fold/ratchet.slow.test.ts`), so the PR's diff shows it piece by piece ([notes/ratchet.md](notes/ratchet.md)). Beside it, `src/engine/fold/midiRatchet.ts` folds the MIDI library (`midi/<set>`, every collection, the files as they come; one test file per set, `midi.<set>.slow.test.ts`) against `src/engine/fold/ratchet.midi.<set>.json`: no file whose fold was taken may lose it, a set's score not grow by more than 1 % (recorded the same way: `UPDATE_RATCHET=1 npx vitest run src/engine/fold/midi.`). Both are in the slow project.
- Probes (`tools/probe/*.test.ts`): measurements of the whole library that answer a design question (where a cell sits on the frequency tower, which way a wire leaves its source), not checks; skipped in `npm test`, run with `PROBE=out.txt npx vitest run tools/probe/<name>.test.ts`, which writes their tables to `out.txt`. The `probe` skill (`.claude/skills/probe/SKILL.md`) says how to write one and where its findings go.
- Examples page: `src/examplesDoc.test.ts` fails if `docs/examples.md` differs from what `tools/examples-doc.ts` writes from `examples/*.cells`; `npm run docs:examples` regenerates it (do it in the PR that changes an example's title, tags, label, postgain or length).
- Layering: `src/architecture.test.ts` fails if a non-test file in `engine/` or `layout/` imports Svelte, Tone, `@xyflow`, `audio/` or `ui/`.
- Docs: `src/docs.test.ts` compiles every ```` ```cells ```` block under `docs/language/` with no diagnostics, checks `docs/INDEX.md` lists each page, and that relative links resolve.
