# Testing

What the tests promise and how to run them; see [architecture.md](architecture.md) for the code they cover.

## Run

CI (`.github/workflows/ci.yml`, Node 22) is the gate on every PR and on `main` (the ruleset requires the `check` job; see [decision 004](decisions/004-agents-dont-merge.md#the-ruleset)):

- `check` job: `npm run check` (svelte-check with `--tsgo`: the TypeScript diagnostics come from the native compiler, `@typescript/native-preview`, pinned; the same diagnostics as `tsc` in about a third of the time), `npm run lint` (ESLint: `typescript-eslint` and `eslint-plugin-svelte`, `eslint.config.js`; errors fail, warnings are listed), `npm run format:check` (Prettier: `.prettierrc.json`, `.prettierignore`; `npm run format` fixes), `npm run knip` (unused exports, files and dependencies: `knip.json`), `npm test` (`vitest run`; `npm run test:watch` while editing), `npm run build`. It uploads the build.
- Smoke test (`.github/workflows/smoke.yml`, not part of `ci.yml`): `npm run smoke` on a fresh build, in the runner's Chrome: `tools/smoke.mjs` opens every piece of the library and presses Play (its voices are built and its first window is asked for), and plays in full, for 2 s, the fewest pieces that between them use every kind of audio node: each voice source and body, every sound parameter set or moving, tapes and their parts, kits, gates, bends, envelopes (`tools/smoke-pick.ts` works them out from what each example compiles to, so a new example that brings a new kind of sound is played by itself; `npm run smoke -- --list` says which and why). It fails on any page error, console error, or an AudioContext that isn't running (and, played in full, advancing). This is the only check that builds the audio graph of every voice kind (tapes, resonators, FM, kits), since vitest has no Web Audio. `--all` plays every piece in full. It takes a minute or two and runs on every PR that isn't a draft (on open, each push, reopen, ready for review); `main` doesn't run it. It isn't a required check: whoever merges waits for it on the head (the `senior` skill).
- The build is a PWA (`vite-plugin-pwa` in `vite.config.ts`): `dist/sw.js` precaches the shell and the Tone chunk; a new version waits for the user (`src/ui/UpdateToast.svelte`). `base` is `./`, so the same `dist/` works under `/cell-studio/` or any preview folder.
- `deploy` job (`main` only): publishes the `check` job's build to the root of gh-pages, keeping the `pr-<n>/` folders; it doesn't test or build again. A deploy running is never cancelled; a run whose commit is no longer the head of `main` skips, so the newest commit is the one that ends up live.
- `preview` job (PRs from branches of this repository, drafts too; not forks or Dependabot, whose token can't write): publishes the PR's build to `gh-pages/pr-<n>/`, at `https://yggi.github.io/cell-studio/pr-<n>/`, to try it on a phone before merging, and keeps one comment on the PR with the address (found by a hidden marker and edited on each push). `.github/workflows/preview-cleanup.yml` removes the folder when the PR closes (merged or not) and says so in that comment; by hand (Actions → Preview cleanup → Run workflow, a PR number) for one left behind. The build is of the PR merged with `main`, as the `check` job tests it.
- Every gh-pages writer goes through `.github/scripts/pages.sh` (`main`, `preview <n>`, `remove <n>`): it makes gh-pages one fresh commit (no history of builds, as before) from the branch as it is, and pushes it with a lease on the commit it started from; if another writer got there first it starts again from theirs, so none overwrites another's folder. Concurrency groups only order the runs of one writer (`pages-main`; `pages-pr-<n>` for a PR's preview and its removal, a newer one cancelling the older): GitHub keeps one pending run per group and cancels the one before, so a single group for every writer could drop a removal or a preview.
- A preview shares the origin with the app: `src/storageKey.ts` gives its kept settings (`?latency=`, `?lookahead=`, `?perf`, the engine, the library's layout) keys of its own (`pr-12/cell-studio-latency`); the app keeps the plain keys. Saved pieces are shared, so a preview can open yours. The app's service worker doesn't answer for `pr-<n>/` pages (`navigateFallbackDenylist` in `vite.config.ts`), which would otherwise be served the app's own page.

Locally, run `npm test && npm run check && npm run lint && npm run format:check` before pushing, and one file while iterating (`npx vitest run src/engine/parser/parser.test.ts`, or `npx vitest run --changed`: the tests that import what you changed). Run the smoke test only when you changed what it covers (audio, UI wiring, assets, `vite.config.ts`): `npm run build && npm run smoke -- 2 "Music Box"` (seconds, then piece-title words, each played in full; all pieces if none). In a cloud session set `CHROME_PATH=/opt/pw-browsers/chromium`.

Tests are `*.test.ts` beside their source, in node (no isolation between files, and transformed modules cached on disk: `vite.config.ts`). Vitest runs files in parallel, not the tests in a file: a sweep over the whole library goes in a file of its own (`physics.library.test.ts`) and does each piece’s work once for all its checks. Being in node, they can only cover `engine/`, `layout/`, `theory/`, the audio engines (not Web Audio), a few `ui/` helpers, the examples and the docs.

## Groups

- Theory: `src/theory/modes.test.ts`.
- Parser: `parser/parser.test.ts`. The syntax reference: `parser/reference.test.ts` parses every example in `docs/language/reference.md` (generated by `tools/reference.ts` from the parser's tables), checks it covers every generator, `map=` kind, unit, modifier, attribute and parameter, and that the committed page is current (record it: `UPDATE_REFERENCE=1 npx vitest run src/engine/parser/reference.test.ts`). Compile: `compiler/compile.test.ts`, `duration.test.ts`, `physics.test.ts`, `fiveto12.test.ts`.
- Realize (what sounds): `realize.test.ts` (notes, times, levels, per example), `tape.test.ts`, `resonator.test.ts`, `fm.test.ts`, `wave.test.ts`; `edit.test.ts` for line rewrites; `schedule.test.ts` (windows, the engine host).
- Routing (what the graph draws as sounding): `routing.test.ts`: the cases of #11, and for every example that routed and live states agree (live within routed, edges with routed ends, every routed edge drawn), every voice that plays is routed and live while its note sounds, and what moves a voice is routed.
- Audio: `src/audio/engine.test.ts` (local and worker engines; no Web Audio needed).
- Layout: `src/layout/*.test.ts` (belts, cellview, describe, dial, geometry, labels, physics, quality, show, spectrum); `physics.library.test.ts` lays out every example (three times, for the quality gate).
- Examples: `src/engine/examples.test.ts` — every `examples/*.cells` file is listed, compiles with zero diagnostics, and has a title, tags and `level=`.
- Fuzz: `src/engine/fuzz.test.ts` — every example with one token or character deleted (a seeded sample of 20 each) compiles, plans and plays its first seconds without throwing. A program with errors plays nothing (`plan` returns no tracks): it may name cells it doesn't have.
- UI helpers: `src/ui/colour`, `highlight`, `suggest` tests.

## Promises

- Shorten (`src/engine/compress.ts`) preserves every note: `compress.test.ts` runs `shorten` on every preset; each suggestion is shorter and `sounds()` is identical (events from `plan` + `eventsBetween`). `shortenAll` is tested too.
- BWV 847: `tools/bwv847.reference.json` (written by `tools/bwv847.py`, which downloads the CCARH encoding itself and also writes `examples/bwv847.cells`) is checked note by note in `realize.test.ts`: onset, length and pitch per voice, as sounded through the tempo map.
- Counterpoint: the Ricercar's passes obey the species rules in `realize.test.ts` (`problems(...)` on what sounds, also per tonos). `tools/counterpoint.py` searched for the lines under the same species rules.
- Loudness: not in vitest (needs Web Audio). Measure in the browser with `window.cellStudio` (defined in `src/debugHook.ts`):
  - `await cellStudio.measure(seconds?)` renders offline, returns `{ rms, peak, clipped }` (dB below full scale; `clipped` counts samples at the ceiling).
  - `cellStudio.length()`: default render length in seconds.
  - `cellStudio.level(name)`: a voice's current peak level, or `null`.
  - `await cellStudio.render(source, seconds?)`: renders any source (not only the open piece); adds `hash` (of the samples) and `blocks` (the level of every 2048 samples).
  - `cellStudio.engine()`: how the engine's windows went (which engine, how many, compute and round-trip ms, how many a worker answered too late).
- A piece sounds the same every time (#37), as far as our code goes: none of it draws on `Math.random`; noise, a resonator's bow and where a noise note starts come from our own seeded generator (`src/audio/voice/noise.ts`) and the cell's `seed` (as chance does). Tone.js is left alone, and two parts of it draw on `Math.random`: the reverb's impulse and a tape's hiss. Two guards: `src/audio/repeatable.test.ts` (CI) scans `engine/`, `layout/` and `audio/` for `Math.random` and names the line; `tools/repeatable.mjs` (browser, `npm run build && node tools/repeatable.mjs 6 [piece words]`, not in CI) seeds `Math.random` before each render (so Tone's part repeats), renders every example twice, fails on a call from our code (and prints the caller) and on two renders that differ beyond −100 dB. Not bit for bit: Chromium sums three or more inputs of a node in a changing order (about −180 dB; measured with plain oscillators into one gain). Forks and kalimba are listed as known (#65).
- Golden renders (audio refactors): `tools/golden.mjs` renders every example offline in the browser and compares block levels with a recorded run: record on the base commit (`npm run build && node tools/golden.mjs 6 > /tmp/golden.json`), then check the change (`… --check /tmp/golden.json`). Within −80 dB counts as the same; forks and kalimba vary by up to about −45 dB from run to run on their own (a resonator strike's nodes are disconnected while the offline render runs), so a differing piece is rendered twice more before it counts. Not in CI yet (#18).
- Engines (#15): `src/engine/schedule.test.ts` (windows match `eventsBetween` and survive a structured clone; the host mirrors hands), `src/audio/engine.test.ts` (the worker engine through a fake port: same windows, a late or failed worker falls back to the local plan). In the browser: `ENGINE=worker npm run smoke` plays every piece with the engine in a Web Worker.
- Graph states in the browser: `tools/shots.mjs` plays pieces and saves a screenshot and each node's and edge's drawn state (`npm run build && node tools/shots.mjs 3 "Sound on Tape"`; `DIST=` another build to compare).
- Every graph at once: `tools/graphs.mjs` draws every example's miniature, as the library draws it, on one contact sheet with its crossings, overlapping clusters and intruders from the layout's baseline (`CHROME_PATH=/opt/pw-browsers/chromium node tools/graphs.mjs`, no build, a few seconds; writes `shots/graphs/sheet.png`).
- The gallery (`tools/gallery.mjs <wheels|edges|golden|mockups>`): contact sheets of how the graph draws things, one picture per kind. `golden` renders one piece, `tools/gallery/golden/golden.cells`, with a value of every kind of wheel and edge the examples draw, in the real graph laid out by the app (`golden.test.ts` checks its coverage and its layout); `wheels` plays every piece in the built app and keeps every kind of wheel (graph, petals, a cell's sheet, the library) in its liveliest state (`npm run build && node tools/gallery.mjs wheels`; writes `shots/wheels/sheet.png`); `--fast`, and `edges` (every kind of edge in every state, on bare nodes) and `mockups` (design questions side by side), set everything up directly instead (`tools/gallery/harness.html`, from the working tree, no build, ~15 s). The `gallery` skill (`.claude/skills/gallery/SKILL.md`) says how to read them and compare before / after.
- Layout quality (#27): `src/layout/quality.ts` measures a layout: drawn crossings, the box, mean edge length, the worst overlap, overlapping tag clusters and cells inside a cluster they don't carry. `physics.library.test.ts` measures every example (and its crossings before the physics, `start`), each number the mean of three starts (seeds 0, 1, 2), and compares the library's totals with `src/layout/quality.baseline.json`: crossings (and their cost), clusters, intruders and read heads' aim may not grow, the area not by more than 5 %. A layout change that is worth its trade records the new numbers (`UPDATE_LAYOUT_BASELINE=1 npx vitest run src/layout/physics.library.test.ts`), so the PR's diff of the baseline shows what it did, piece by piece. One layout is one draw: neighbouring settings move the library's crossings by ±15, so compare a change over several starts (`seed`, a layout option: which small nudges new nodes get; 0 is the app's), as in [notes/27-layout.md](notes/27-layout.md).
- Examples page: `src/examplesDoc.test.ts` fails if `docs/examples.md` differs from what `tools/examples-doc.ts` writes from `examples/*.cells`; `npm run docs:examples` regenerates it (do it in the PR that changes an example's title, tags, label, level or length).
- Layering: `src/architecture.test.ts` fails if a non-test file in `engine/` or `layout/` imports Svelte, Tone, `@xyflow`, `audio/` or `ui/`.
- Docs: `src/docs.test.ts` compiles every ```` ```cells ```` block under `docs/language/` with no diagnostics, checks `docs/INDEX.md` lists each page, and that relative links resolve.
