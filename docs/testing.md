# Testing

What the tests promise and how to run them; see [architecture.md](architecture.md) for the code they cover.

## Run

**The gate is local:** `npm run verify` before every push, where it costs nothing, and the PR names the commit that passed it and what else ran (its *Verified* section). CI is a witness, sized to the family's budget ([CI-BUDGET.md](https://github.com/yggi/music-commons/blob/main/CI-BUDGET.md)): one job, once per push to a PR that is ready. No check is required to merge ([decision 004](decisions/004-agents-dont-merge.md#the-ruleset)).

- `npm run verify`: first, in a checkout with no `node_modules` (a git worktree an agent opens has none), `npm ci`, and it says so (`tools/install-first.mjs`); then `npm run check` (svelte-check with `--tsgo`: the TypeScript diagnostics come from the native compiler, `@typescript/native-preview`, pinned; the same diagnostics as `tsc` in about a third of the time; then `tools/strict.mjs`, a ratchet: `src/**/*.ts` checked with `noUncheckedIndexedAccess` (`tsconfig.strict.json`; not tests, not `.svelte`), failing on any error in a folder on its clean list, `audio/`, `midi/`, `ui/*.ts`, `ui/state/`, `ui/kit/` (the engine and the theory are held by yggi/cells' own copy of this ratchet), and of the layout `envelope.ts`, `glyph.ts`, `timelayers.ts`, `timepictures.ts` (#320: new code goes on clean); a folder made clean goes on the list), `npm run lint` (ESLint: `typescript-eslint` and `eslint-plugin-svelte`, `eslint.config.js`; errors fail, warnings are listed), `npm run format:check` (Prettier: `.prettierrc.json`, `.prettierignore`; `npm run format` fixes), `npm run knip` (unused exports, files and dependencies: `knip.json`), then `npm test` (below). It stops at the first that fails.
- The pre-push hook (`.githooks/pre-push`; `npm install`'s `prepare` and `.claude/hooks/session-start.sh` set `core.hooksPath` to `.githooks`) runs `npm run verify` before every push of a branch and blocks one that fails. It refuses a push while a tracked file has uncommitted changes (verify checks the tree, the push sends the commit), while an untracked file git doesn't ignore is in the tree (verify would see it, the commit lacks it; unless the commit's tree passed already), or of a commit other than the one checked out; keeps a failed run's whole output in the git directory (`cell-studio-verify-failed.log`) and names it; prints one line when it lets a push through, with the number of tests that passed. A tree that passed is stamped in the git directory (`cell-studio-verified`, a line `<tree> <tests passed>`), by the hook or by `npm run verify` itself (`tools/verified.mjs`: `preverify` records the tree of every file verify is about to see, tracked or not, but not ignored, through a scratch index; `postverify` stamps it with the count `npm test`'s reporter `tools/test-count.mjs` keeps, unless a file changed while verify ran), so a push of a commit of exactly those files isn't verified again, and one that leaves a file out is. A branch that differs from `origin/main` in `*.md` alone runs the docs-only check (`format:check` and the docs tests) and isn't stamped. A deletion, a tag and the deploy's push to `gh-pages` check nothing. Its tests: `tools/hooks.test.ts`.
- CI (`.github/workflows/ci.yml`, Node 22), one job, `check`, on a PR opened, pushed to, reopened or taken out of draft (a draft runs nothing, and a newer push cancels the run still going): the four checks of `npm run verify`, then the quick project of the tests (`vitest run --project quick`; `npm test` on CI would run every slow test, below). Each runs even when one before it failed, so one run gives every verdict. By hand (Actions → CI → Run workflow, `all` ticked) it also runs the slow project (`*.slow.test.ts`: the folder over whole pieces and over the MIDI library, the ratchets) and `npm run build`. It doesn't deploy: `node tools/deploy.mjs` does (below).
- Smoke test (`.github/workflows/smoke.yml`, by hand only: Actions → Smoke → Run workflow; or locally, below), one job: `npm run smoke` on a fresh build, in the runner's Chrome: `tools/smoke.mjs` opens every piece of the library and presses Play (its voices are built and its first window is asked for), and plays in full, for 2 s, the fewest pieces that between them use every kind of audio node: each voice source and body, every sound parameter set or moving, tapes and their parts, kits, gates, bends, envelopes (`tools/smoke-pick.ts` works them out from what each example compiles to, so a new example that brings a new kind of sound is played by itself; `npm run smoke -- --list` says which and why). It fails on any page error, console error, or an AudioContext that isn't running (and, played in full, advancing). This is the only check that builds the audio graph of every voice kind (tapes, resonators, FM, kits), since vitest has no Web Audio. `--all` plays every piece in full. Then `tools/repeatable.mjs 4` renders every example offline twice, 4 s each: the two renders must be **the same sound** (below), none of our code may call `Math.random`, and no piece may clip or go over the loudness ceiling (peak −1 dB, average −18 dB; a ceiling only, since 4 s of a quiet start averages far under the piece's −24 dB). Together they take a few minutes, on one build; the renders run even when the smoke test failed. Run them, here or locally, when a change reaches what they cover (audio, UI wiring, assets, `vite.config.ts`), and say in the PR on which commit.
- The build is a PWA (`vite-plugin-pwa` in `vite.config.ts`): `dist/sw.js` precaches the shell and the Tone chunk; a new version waits for the user (`src/ui/UpdateToast.svelte`). `base` is `./`, so the same `dist/` works under `/cell-studio/` or any preview folder.
- `preview.yml` (on demand: put the `preview` label on a PR from a branch of this repository; not forks or Dependabot, whose token can't write): builds the PR on its own (no tests, so labelling re-runs nothing) and publishes it to `gh-pages/pr-<n>/`, at `https://yggi.github.io/cell-studio/pr-<n>/`, to try it on a phone before merging, rebuilt on every push while the label is on, with one comment on the PR with the address (found by a hidden marker and edited). Most PRs never need one, so none is made by default. `.github/workflows/preview-cleanup.yml` removes the folder when the PR closes with the label on, or the label is taken off, and says so in that comment; by hand (Actions → Preview cleanup → Run workflow, a PR number) for one left behind. By hand too: Actions → Preview → Run workflow, a PR number. The build is of the PR merged with `main`, as CI tests it.
- Every gh-pages writer goes through `.github/scripts/pages.sh` (`main` from `tools/deploy.mjs`, `preview <n>`, `remove <n>`): it makes gh-pages one fresh commit (no history of builds, as before) from the branch as it is, and pushes it with a lease on the commit it started from; if another writer got there first it starts again from theirs, so none overwrites another's folder. Concurrency groups only order the runs of one writer (`pages-pr-<n>` for a PR's preview and its removal, a newer one cancelling the older): GitHub keeps one pending run per group and cancels the one before, so a single group for every writer could drop a removal or a preview.
- A preview shares the origin with the app: `src/storageKey.ts` gives its kept settings (`?latency=`, `?lookahead=`, `?perf`, the engine, the library's layout) keys of its own (`pr-12/cell-studio-latency`); the app keeps the plain keys. Saved pieces too (`library.ts`): a PR that changes how pieces are saved can't touch yours. The app's service worker doesn't answer for `pr-<n>/` pages (`navigateFallbackDenylist` in `vite.config.ts`), which would otherwise be served the app's own page.

Locally, run `npm run verify` before pushing (for docs alone, [AGENTS.md](../AGENTS.md#checks) names less), and one file while iterating (`npx vitest run src/layout/library.test.ts`, or `npx vitest run --changed`: the tests that import what you changed). Run the smoke test only when you changed what it covers (audio, UI wiring, assets, `vite.config.ts`): `npm run build && npm run smoke -- 2 "Music Box"` (seconds, then piece-title words, each played in full; all pieces if none). In a cloud session set `CHROME_PATH=/opt/pw-browsers/chromium`.

### What `npm test` runs

`npm test` (`tools/test.mjs`) runs every quick test, and a slow test only when the change reaches it: when the slow file, or anything it imports, differs from `origin/main` (committed, staged, changed or new: vitest's `--changed`), or a file the tests read from disk moved (`forceRerunTriggers` in `vite.config.ts`: `examples/`, `midi/`, the BWV 847 reference, the lockfile). It says which slow files it runs and why; the picked ones share one vitest run with the quick ones. Every slow test runs when `CI` is set, with no `origin/main` to compare with, or when vitest can't list what changed. `npm test -- --all` (or `npm run test:all`) runs everything; `npm run test:slow` the slow project alone; `npm test -- <file>` runs what you name, in whichever project.

- **Quick or slow.** A test belongs in the slow project (`name.slow.test.ts`) when it takes more than a few seconds idle: a sweep that folds whole pieces, or a ratchet over a library. Quick tests have 20 s each (`testTimeout`) and show their time past 5 s (`slowTestThreshold`): one that does, often, is a candidate for the slow project. Slow tests have 10 min each: a budget for a loaded machine, not a measure; they fail on what they find, not on the clock (#361).
- **Idle, on 4 cores:** `npm test` for a change that doesn't reach the slow tests (UI, layout, docs) about 1 min; one that does (the engine, the folder, an example, a MIDI file) about 2½ min, as `test:all`. Before the split every `npm test` took 3 min, a 103 s test (the whole MIDI library folded in one file) its critical path; the library's ratchet now runs one file per collection (`fold/midiRatchet.ts`), side by side.

### Fail-safes

- **A stale build.** `smoke`, `repeatable`, `golden` and `shots` test `dist/`, not the source: each stops if a file the build is made from (`src/`, `public/`, `examples/`, `index.html`, `vite.config.ts`, the lockfile; not tests) is newer than `dist/index.html`, and names it (`tools/fresh-build.mjs`). `STALE_BUILD=1` tests the build as it is; `shots` with `DIST=` skips it (another build, on purpose).
- **A stale type-check cache.** `npm run check` first removes what svelte-check transpiled for components that are gone (`tools/check-stale.mjs`): a deleted component's leftovers in `.svelte-check/` reported errors from code that no longer exists.
- **The deploy, by hand** (CI doesn't deploy, #300): `node tools/deploy.mjs` refuses a tree with changes or a HEAD that isn't `origin/main`'s, runs every check (`test:all`, slow tests too), builds afresh and only then publishes to the root of gh-pages with `.github/scripts/pages.sh`, keeping the `pr-<n>/` folders. `--dry-run` stops before publishing. Then `node tools/live.mjs` checks the live site serves that build: the live page's module script is `dist/index.html`'s (asked every 10 s while Pages publishes, up to 10 min), and the page opens in Chromium with no console error ([the `land` skill](../.claude/skills/land/SKILL.md)).
- **Actions blocked.** A CI run that fails within seconds, with no runner and no step, is Actions blocked (the account's minutes used up, or Actions switched off), not a verdict on the change. `node tools/measure/actions.mjs --status yggi/cell-studio`, in [music-commons](https://github.com/yggi/music-commons/blob/main/CI-BUDGET.md), tells a blocked repository from one where Actions runs. The evidence is the verified commit the PR names; when minutes are back, one run of a blocked check on a PR still open is enough. Nothing waits on Actions: no check is required, and the deploy runs from a session.
- **A MIDI collection without its ratchet** is caught in yggi/cells, where the MIDI collections and the folder's ratchets live (its `fold/midi.sets.test.ts`).
- **Timing in the browser.** The smoke test's take (#210, #360) stamps each key with the moment its step is heard (`cellStudio.heardAt`), as a real MIDI message carries its `timeStamp`, and aims at the pass the recorder placed (`cellStudio.take()`): a loaded machine sending a key late doesn't move it. Under five busy loops on 4 cores the old check failed 3 runs of 3, the new one passed 3 of 3.

Tests are `*.test.ts` beside their source, in node (no isolation between files, and transformed modules cached on disk: `vite.config.ts`). Vitest runs files in parallel, not the tests in a file: a sweep over the whole library goes in a file of its own (`physics.library.test.ts`) and does each piece’s work once for all its checks. Being in node, they can only cover `engine/`, `layout/`, `theory/`, the audio engines (not Web Audio), a few `ui/` helpers, the examples and the docs.

## Groups

The language's own tests (the theory, the parser and its reference, what realizes and what routes, the examples, the snapshot, the equivalences, the fuzz, Shorten's promise, BWV 847, counterpoint, the engine host, the folder's ratchet) live in [yggi/cells](https://github.com/yggi/cells) with the code: [its testing page](https://github.com/yggi/cells/blob/main/docs/testing.md). Here are the cases of them that read the drawing (`src/layout/*.drawn.test.ts`) and the library's index (`src/examplesIndex.test.ts`).

- Audio: `src/audio/engine.test.ts` (local and worker engines; no Web Audio needed).
- Layout: `src/layout/*.test.ts` (belts, cellview, describe, dial, geometry, labels, physics, quality, show, spectrum); `physics.library.test.ts` lays out every example (three times, for the quality gate).
- UI helpers: `src/ui/colour`, `highlight`, `suggest` tests.

## Promises

- Loudness: not in vitest (needs Web Audio). Measure in the browser with `window.cellStudio` (defined in `src/debugHook.ts`):
  - `await cellStudio.measure(seconds?)` renders offline, returns `{ rms, peak, clipped }` (dB below full scale; `clipped` counts samples at the ceiling).
  - `cellStudio.length()`: default render length in seconds.
  - `cellStudio.level(name)`: a voice's current peak level, or `null`.
  - `cellStudio.transport()`: `{ state, seconds }`, the transport's state and where the piece is heard (code seconds).
  - `await cellStudio.render(source, seconds?)`: renders any source (not only the open piece); adds `hash` (of the samples) and `blocks` (the level of every 2048 samples).
  - `cellStudio.engine()`: how the engine's windows went (which engine, how many, compute and round-trip ms, how many a worker answered too late).
  - `cellStudio.open(source, name?)`: opens a string of code as the open piece, the way opening a file does (`Studio.openSource`; `name` the file's, by default from its title): the editor, the graph and Play follow it, the transport stops, and what was open is replaced unasked and unsaved, as a file replaces it. Returns `{ ok, errors }`: whether it compiled, and the errors' messages (one that doesn't compile opens too, as a file's would). The smoke test opens one over a piece playing (#406).
- **The same sound** means two renders whose levels agree block by block (every 2048 samples) within −100 dB: far below hearing and below the 0.1 dB the loudness checks work in. Bit for bit is neither reachable nor needed (below).
- A piece sounds the same every time (#37), as far as our code goes: none of it draws on `Math.random`; noise, a resonator's bow and where a noise note starts come from our own seeded generator (`src/audio/voice/noise.ts`) and the cell's `seed` (as chance does). Tone.js is left alone, and two parts of it draw on `Math.random`: the reverb's impulse and a tape's hiss. Two guards: `src/audio/repeatable.test.ts` (CI) scans `engine/`, `layout/` and `audio/` for `Math.random` and names the line; `tools/repeatable.mjs` (browser, `npm run build && node tools/repeatable.mjs 6 [piece words]`; the smoke workflow runs it at 4 s) seeds `Math.random` before each render (so Tone's part repeats), renders every example twice, fails on a call from our code (and prints the caller) and on two renders that differ beyond −100 dB. Not bit for bit: Chromium sums three or more inputs of a node in a changing order (about −180 dB; measured with plain oscillators into one gain). Forks and kalimba are listed as known (#65): their resonators form a feedback loop (`couple=`, a board), and Chromium seems to process a loop starting from a node that changes from run to run, so a link runs a block late (up to about −45 dB; without the loop both repeat bit for bit). Accepted: it can't be heard live, and only a worklet holding the whole coupled bank would make it repeat (#17).
- The corpus yardstick (#10, language and example changes): `tools/corpus.mjs` measures every example (characters, lines, cells, diagnostics, what Shorten still finds) and fingerprints the notes it plays (voice, onset, length, frequency and gains over 0–120 s, from `plan` + `eventsBetween`). Record on the base (`node tools/corpus.mjs > /tmp/corpus.json`), then check the change (`node tools/corpus.mjs --check /tmp/corpus.json`): it lists each piece whose notes or code moved and exits 1 when a piece sounds different, except those named with `--expect "acid,pop"` (the ones meant to). No build, a few seconds; notes, not audio (an audio change is `tools/golden.mjs`).
- Golden renders (audio refactors): `tools/golden.mjs` renders every example offline in the browser and compares block levels with a recorded run: record on the base commit (`npm run build && node tools/golden.mjs 6 > /tmp/golden.json`), then check the change (`… --check /tmp/golden.json`). Within −80 dB counts as the same; forks and kalimba vary by up to about −45 dB from run to run on their own (their feedback loops, #65), so a differing piece is rendered twice more before it counts. Not in CI: a stored golden needs a way to say a change to a sound is intended (#92); the repeatability run above and the event snapshot (#142) are what the checks hold.
- Engines (#15): the host's own tests are cells' (`engine/schedule.test.ts`); `src/audio/engine.test.ts` (the worker engine through a fake port: same windows, a late or failed worker falls back to the local plan). In the browser: `ENGINE=worker npm run smoke` plays every piece with the engine in a Web Worker.
- Graph states in the browser: `node tools/gallery.mjs play` plays pieces and saves a screenshot and each node's and edge's drawn state (`node tools/gallery.mjs play 3 "Sound on Tape"`; `DIST=` another build to compare).
- Keyboard focus (#135): `tools/tabwalk.mjs` Tabs through the start view, the sidebar (Files, MIDI, the layout forces), Shorten, the legend, add a cell, the cards, a library piece, a cell's sheet and (at phone width) the Graph and Code tabs, and lists each stop whose computed outline and box-shadow draw nothing (`CHROME_PATH=/opt/pw-browsers/chromium node tools/tabwalk.mjs [stops] [view words]`, no build, the first load is slow; exits 1 when a stop has no ring). It checks that a ring is drawn, not what it looks like; a view it can't open is reported, and counts as a failure.
- Every graph at once: `tools/graphs.mjs` draws every example's miniature, as the library draws it, on one contact sheet with its crossings, overlapping clusters and intruders from the layout's baseline (`CHROME_PATH=/opt/pw-browsers/chromium node tools/graphs.mjs`, no build, a few seconds; writes `shots/graphs/sheet.png`).
- The gallery (`tools/gallery.mjs <wheels|edges|golden|mockups>`): contact sheets of how the graph draws things, one picture per kind. `golden` renders one piece, `tools/gallery/golden/golden.cells`, with a value of every kind of wheel and edge the examples draw, in the real graph laid out by the app (`golden.test.ts` checks its coverage and its layout); `wheels` plays every piece in the built app and keeps every kind of wheel (graph, petals, a cell's sheet, the library) in its liveliest state (`npm run build && node tools/gallery.mjs wheels`; writes `shots/wheels/sheet.png`); `--fast`, and `edges` (every kind of edge in every state, on bare nodes) and `mockups` (design questions side by side), set everything up directly instead (`tools/gallery/harness.html`, from the working tree, no build, ~15 s). The `gallery` skill (`.claude/skills/gallery/SKILL.md`) says how to read them and compare before / after.
- Layout quality (#27): `src/layout/quality.ts` measures a layout: drawn crossings, the box, mean edge length, the worst overlap, overlapping tag clusters and cells inside a cluster they don't carry. `physics.library.test.ts` measures every example (and its crossings before the physics, `start`), each number the mean of three starts (seeds 0, 1, 2), and compares the library's totals with `src/layout/quality.baseline.json`: crossings (and their cost), clusters, intruders and read heads' aim may not grow, the area not by more than 5 %. A layout change that is worth its trade records the new numbers (`UPDATE_LAYOUT_BASELINE=1 npx vitest run src/layout/physics.library.test.ts`), so the PR's diff of the baseline shows what it did, piece by piece. One layout is one draw: neighbouring settings move the library's crossings by ±15, so compare a change over several starts (`seed`, a layout option: which small nudges new nodes get; 0 is the app's), as in [notes/27-layout.md](notes/27-layout.md).
- Probes (`tools/probe/*.test.ts`): measurements of the whole library that answer a design question (where a cell sits on the frequency tower, which way a wire leaves its source), not checks; skipped in `npm test`, run with `PROBE=out.txt npx vitest run tools/probe/<name>.test.ts`, which writes their tables to `out.txt`. The `probe` skill (`.claude/skills/probe/SKILL.md`) says how to write one and where its findings go.
- Examples page: `src/examplesDoc.test.ts` fails if `docs/examples.md` differs from what `tools/examples-doc.ts` writes from the package's `examples/*.cells`; `npm run docs:examples` regenerates it (do it in the PR that changes an example's title, tags, label, postgain or length).
- Layering: `src/architecture.test.ts` fails if a non-test file in `layout/` imports Svelte, Tone, `@xyflow`, `audio/` or `ui/` (the language's purity is cells' own gate).
- The boot reading: `tools/reading-list.test.ts` fails when `AGENTS.md` and `docs/MEMORY.md`, what an agent reads first, together pass 28 KB (`tools/reading-list.ts`). Past it, condense them as a change of its own: a fact moves to its page in `docs/`, MEMORY keeps the pointer.
- Docs: `src/docs.test.ts` compiles every ```` ```cells ```` block in these docs with no diagnostics (the language's pages are cells'), checks `docs/INDEX.md` lists each page, and that relative links resolve.
